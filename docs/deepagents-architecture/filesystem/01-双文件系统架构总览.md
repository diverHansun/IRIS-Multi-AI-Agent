# 双文件系统架构总览

## 1. 背景与问题

### 1.1 现有架构的局限

当前项目中的虚拟文件系统（Virtual Filesystem）基于 LangGraph 的状态管理和持久化存储实现，所有文件数据存储在内存和数据库中，完全与宿主机的真实文件系统隔离。

**核心问题：**

虚拟文件系统无法访问宿主机的真实文件，导致 Agent 无法直接读取用户的项目代码、配置文件和文档。这严重限制了 Agent 的实用价值，使其无法完成诸如"分析项目代码结构"、"阅读 README 文档"等基本任务。

### 1.2 设计目标

引入双文件系统架构，同时支持虚拟文件系统和真实文件系统，各司其职：

**虚拟文件系统：** Agent 的内部工作空间和长期记忆存储
**真实文件系统：** 宿主机文件的只读信息获取

通过这种设计，Agent 既能获取外部信息，又能安全地进行内部数据管理。

---

## 2. 架构设计

### 2.1 双文件系统职责划分

#### 虚拟文件系统（Virtual Filesystem）

**定位：** Agent 的内部工作空间

**核心职责：**

- 临时数据存储：Agent 执行过程中的草稿、中间结果
- 长期记忆持久化：跨会话保留的信息（使用 `/memories/` 路径前缀）
- Multi-Agent 通信：不同 Agent 之间的数据共享媒介
- 大结果缓存：工具输出过大时的驱逐存储
- 会话状态管理：对话上下文和临时数据

**特点：**

- 完全隔离，用户不可见
- 支持全部操作：读、写、编辑、列表
- 数据存储在内存或 LangGraph Store
- 无需权限控制（沙箱环境）

---

#### 真实文件系统（Real Filesystem）

**定位：** 宿主机文件的只读信息获取

**核心职责：**

- 代码库读取：分析项目源代码
- 配置文件读取：获取项目配置信息
- 文档读取：阅读 README、API 文档
- 文件搜索：通过 Glob 和 Grep 搜索特定文件和内容
- 文件元信息：获取文件列表、大小、修改时间

**特点：**

- 直接访问宿主机文件系统
- 仅支持只读操作：读、列表、搜索
- 不支持：写入、编辑、Bash 命令
- 严格的权限控制（路径白名单）

---

### 2.2 工具集对比

| 操作类型 | 虚拟文件系统 | 真实文件系统 | 说明 |
|---------|-------------|-------------|------|
| 列出文件 | `list_virtual_files` | `list_real_files` | 枚举文件列表 |
| 读取文件 | `read_virtual_file` | `read_real_file` | 读取文件内容 |
| 写入文件 | `write_virtual_file` | 不支持 | 创建新文件 |
| 编辑文件 | `edit_virtual_file` | 不支持 | 修改已有文件 |
| 模式匹配 | 不支持 | `glob_real_files` | 按通配符搜索文件 |
| 内容搜索 | 不支持 | `grep_real_files` | 按正则表达式搜索内容 |
| Shell 命令 | 不支持 | 不支持 | 暂不实现 |

### 2.3 代码组织结构

#### 项目结构

```
src/components/deepagents/runtime_middlewares/
├── virtual_filesystem/              # 虚拟文件系统（现有，重命名）
│   ├── __init__.py
│   ├── middleware.py               # 中间件实现
│   ├── tools.py                    # 工具实现
│   ├── types.py                    # 类型定义
│   └── utils.py                    # 辅助函数
│
└── real_filesystem/                # 真实文件系统（新增）
    ├── __init__.py
    ├── middleware.py               # 中间件实现
    ├── tools.py                    # 工具实现：list/read/glob/grep
    ├── security.py                 # 安全控制：路径白名单
    └── utils.py                    # 辅助函数：路径解析、文件读取
```

#### 配置文件结构

```
config/agents/deep/middleware/
├── virtual_filesystem.json         # 虚拟文件系统配置
└── real_filesystem.json            # 真实文件系统配置
```

---

### 2.4 中间件集成方式

两个文件系统作为独立的中间件注册到 Agent Runtime：

```python
# 伪代码示例
virtual_fs = VirtualFilesystemMiddleware(config=virtual_config)
real_fs = RealFilesystemMiddleware(config=real_config)

agent = DeepAgent(
    middlewares=[virtual_fs, real_fs],
    # ...
)
```

**优势：**

- 职责分离清晰
- 可独立启用或禁用
- 配置互不干扰
- 便于测试和维护

## 3. 使用场景

### 3.1 虚拟文件系统典型场景

**场景1：分析过程记录**

Agent 在分析代码时，将发现的问题记录到虚拟文件中，供后续步骤参考。

**场景2：长期记忆**

Agent 将用户的偏好设置保存到 `/memories/user_preferences.json`，下次对话时自动读取。

**场景3：Multi-Agent 协作**

Agent A 生成分析报告并写入虚拟文件，Agent B 读取该报告并继续处理。

**场景4：大结果缓存**

某工具返回 10MB 的数据，自动驱逐到虚拟文件系统，Agent 可分批读取。

---

### 3.2 真实文件系统典型场景

**场景1：代码分析**

用户请求："分析 src/main.py 的代码结构"
Agent 调用 `read_real_file("/home/user/project/src/main.py")` 读取代码。

**场景2：项目文档阅读**

用户请求："总结项目的 README"
Agent 调用 `read_real_file("/home/user/project/README.md")` 读取文档。

**场景3：文件搜索**

用户请求："找到所有 Python 文件"
Agent 调用 `glob_real_files("/home/user/project/**/*.py")` 搜索文件。

**场景4：代码模式搜索**

用户请求："查找所有异步函数定义"
Agent 调用 `grep_real_files(pattern="async def", file_pattern="*.py")` 搜索内容。

## 4. 安全模型

### 4.1 虚拟文件系统安全

虚拟文件系统完全隔离，不直接访问宿主机文件，因此不需要复杂的安全控制。

**安全措施：**

- 路径规范化：防止路径遍历攻击（如 `..` 或 `~`）
- 文件大小限制：防止内存溢出
- 长期存储命名空间隔离：每个 Assistant ID 独立存储空间

---

### 4.2 真实文件系统安全

真实文件系统直接访问宿主机文件，需要严格的安全控制。

**安全措施：**

- 路径白名单：只能访问配置中明确允许的目录
- 路径黑名单：明确禁止访问的敏感目录
- 文件类型限制：仅允许特定扩展名的文件
- 文件大小限制：防止读取超大文件
- 只读限制：不支持任何写入、编辑、删除操作

## 5. 实施计划

### 5.1 开发阶段

**阶段1：真实文件系统核心功能**

- 实现路径白名单安全控制
- 实现基础工具：list_real_files, read_real_file
- 实现搜索工具：glob_real_files, grep_real_files
- 创建配置文件结构
- 跨平台路径支持

**阶段2：虚拟文件系统重构**

- 重命名现有工具（保持向后兼容）
- 移除不必要的安全限制
- 优化配置文件结构
- 更新文档

**阶段3：集成与测试**

- 两个中间件的协同工作
- System Prompt 更新
- 端到端测试
- 性能优化

---

### 5.2 未来扩展

**第二阶段功能（未来实现）：**

- 审计日志：记录所有真实文件系统操作

- 远程文件系统支持：访问 GitHub、S3 等

## 6. 关键决策记录

**决策1：两个独立的中间件**

理由：职责分离、安全隔离、配置独立、便于维护

**决策2：真实文件系统只读**

理由：降低安全风险、满足主要需求（信息获取）、未来可扩展

**决策3：显式工具命名**

理由：清晰明确、防止误操作、便于审计

**决策4：优先实现真实文件系统**

理由：解决最紧迫的问题（Agent 无法读取宿主机文件）

**决策5：第一版仅实现路径白名单**

理由：快速迭代、满足基本安全需求、权限回调作为高级功能

---

## 7. 总结

双文件系统架构通过职责分离和安全隔离，既保留了虚拟文件系统作为 Agent 内部工作空间的价值，又赋予了 Agent 访问外部信息的能力。

这一设计使 Agent 能够真正理解和分析用户的项目，同时保持系统的安全性和可控性。
